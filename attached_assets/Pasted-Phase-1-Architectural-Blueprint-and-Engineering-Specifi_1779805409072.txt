Phase 1 Architectural Blueprint and Engineering Specification: EverydayTools HubExecutive Engineering SummaryThe following architectural specification details the Phase 1 blueprint for "EverydayTools Hub," an internationalized, client-heavy utility web application engineered for uncompromising performance, rigorous privacy, and absolute reliability. Designed for a global audience, the system is architected upon the Next.js 14 App Router, leveraging strict TypeScript, local WebAssembly (WASM) computation, and a bespoke "Editorial Utility" design language built via Tailwind CSS v3.The primary architectural mandate dictates that computational tasks—ranging from neural-network-driven background removal to intricate document format transposition and metadata sanitization—must execute directly within the client's browser environment utilizing free, open-source libraries. This decentralized processing model achieves zero recurring server API overhead, guarantees absolute user data privacy by ensuring files never leave the local device, and establishes offline-capable toolsets.However, where client-side processing is computationally impossible or technically constrained without commercial licensing (e.g., native layout-engine processing for DOCX to PDF conversion), the architecture demands explicit transparency. In such instances, the blueprint mandates the implementation of clearly demarcated server-side stubs, strictly prohibiting the degradation of user trust through falsified or rasterized outputs. This document comprehensively defines the filesystem routing strategy, internationalization middleware, subsystem interfaces, memory management protocols for heavy client-side processing, user experience standards, and rigorous quality gates required prior to Phase 2 scaffolding.System Architecture and Routing TopologyThe foundational architecture strictly adheres to Next.js 14 conventions while imposing a highly organized, domain-driven directory structure. This separation of concerns ensures that presentation components remain entirely decoupled from complex formatting and cryptographic algorithms, communicating exclusively through strictly typed service interfaces.Directory Structure SpecificationsThe application relies on five primary top-level directories, each serving a distinct architectural purpose.Table 1 delineates the required repository structure and the responsibilities of each module.Directory / File PathArchitectural Responsibility/app/[locale]/layout.tsxThe internationalized root shell, hydrating localized strings, injecting global context providers, and rendering the overarching <Header>, <Footer>, and ad-network shells./app/[locale]/page.tsxThe statically generated homepage, parsing tool metadata to render the central <ToolCard> grid and injecting WebSite JSON-LD schema for search engines./app/[locale]/[tool-slug]/page.tsxIndividual, dynamically routed tool interfaces (e.g., /pdf-converter/page.tsx). This section exhausts the architectural mechanisms underpinning every utility within the EverydayTools Hub catalog.Document and E-Book Processing (documentConversionService.ts)The document conversion subsystem presents complex technical hurdles. The proprietary nature of modern document formats, such as the Office Open XML standard utilized by Microsoft Word, creates severe discrepancies when parsed outside of native layout engines. The service contract dictates the following programmatic interface:TypeScripttype ConversionPair = { from: DocFormat; to: DocFormat }
interface DocumentConversionService {
  getSupportedPairs(): ConversionPair
  convert(file: File, from: DocFormat, to: DocFormat,
          onProgress?: (pct: number) => void): Promise<Blob>
}
The conversion registry is managed in /config/formats.config.ts, mapping supported inputs to viable outputs. The underlying implementation utilizes purpose-built libraries for specific format bridges.Text, HTML, and PDF InteroperabilityConverting PDF files to standard text (TXT) relies on the pdfjs-dist package. To prevent main-thread UI blocking during the parsing of complex PDFs, the library's pdf.worker.mjs is dynamically imported and executed as a Web Worker. Text extraction algorithms iterate through internal page dictionaries, mapping spatial layout nodes to sequential string representations. Conversely, generating PDFs from TXT inputs utilizes pdf-lib. The service generates a new coordinate plane, establishes A4 page boundaries, calculates character wrapping based on font metrics, and paints the string array onto the canvas.Markdown transpositions employ the marked library to construct an intermediate abstract syntax tree. Markdown is parsed into semantic HTML, which can then be piped into PDF rendering scripts or transformed into structured .docx archives via the html-docx-js module.The DOCX Conundrum and Server-Side StubsParsing .docx archives into HTML relies on mammoth.js. This library excels at analyzing the internal XML document.xml structures of a Word file, mapping recognized styles to semantic HTML tags without relying on a server environment. The raw HTML output can subsequently be stripped of tags to yield pure TXT outputs.However, the architecture strictly acknowledges a significant client-side limitation: perfect programmatic generation of DOCX files from PDFs, or visually accurate PDFs from DOCX files, requires complex, proprietary layout engines. Standard open-source client tools attempting DOCX-to-PDF conversions often degrade text into rasterized images using html2canvas and jsPDF, which destroys text selection, accessibility, and file size optimization.Therefore, per the non-negotiable architectural rules, conversion pairs such as DOCX → PDF, PDF → DOCX, ODT → PDF, and RTF → PDF will be explicitly annotated in the service layer with // NOT IMPLEMENTED: Requires proprietary layout engine. These UI options will wire to clearly demarcated server-side stubs that return an explanatory error or a simulated delay. The application will never falsify a conversion by outputting a low-quality, inaccessible rasterized PDF. Additionally, converting EPUB to MOBI format requires the heavy server-side Calibre engine and will similarly feature a documented stub implementation.Table 3 categorizes the complete document conversion implementation strategy.Input FormatOutput FormatImplementation MechanismEngine / LibraryPDFTXT / HTMLClient-side spatial text parsing via Web Workerspdfjs-distTXT / MDPDFClient-side vector canvas paintingpdf-lib, markedDOCXHTML / TXTClient-side XML extraction and mappingmammothHTML / MDDOCXClient-side HTML parsing to Office Open XMLhtml-docx-jsPDFDOCX / EPUBServer-side stub (Layout engine required)Marked StubDOCXPDF / EPUBServer-side stub (Layout engine required)Marked StubODT / RTFPDF / DOCXServer-side stub (Complex format limits) Marked StubEPUBMOBIServer-side stub (Requires Calibre backend)Marked StubImage Conversion Architecture (imageConversionService.ts)The image conversion service is confined entirely to the client's local memory footprint, ensuring rapid batch processing and eliminating bandwidth costs for users uploading heavy media files.The service conforms to this exact contract:TypeScriptinterface ImageConversionOptions {
  quality?: number   // 0–1
  width?: number
  height?: number
  maintainAspectRatio?: boolean
}
interface ImageConversionService {
  getSupportedFormats(): ImageFormat
  convert(file: File, to: ImageFormat, opts: ImageConversionOptions): Promise<Blob>
  convertBatch(files: File, to: ImageFormat, opts: ImageConversionOptions,
               onProgress?: (done: number, total: number) => void): Promise<Blob>
}
The underlying engine leverages the browser's native HTML5 Canvas API. Target files are read via the asynchronous FileReader interface into a standard Image object. The object is drawn to an off-screen <canvas> context, allowing for dimensional manipulation based on the width and height options. The result is exported utilizing the canvas.toBlob(callback, mimeType, quality) method, effectively translating formats between PNG, JPEG, WEBP, AVIF, BMP, GIF, TIFF, and ICO. SVG inputs are rasterized through the same methodology, converting scalable vector graphics into fixed-pixel bitmaps.For High-Efficiency Image Container (HEIC/HEIF) formats, which lack native browser canvas support, the architecture implements the heic2any WASM library. When the service intercepts a .heic blob, it decodes the binary array via the WASM module into a standard internal bitmap format, routing it back into the primary canvas pipeline for resizing or conversion. RAW image support is inherently complex due to the vast array of proprietary camera sensor formats; therefore, the implementation provides basic, partial extraction of the embedded JPEG preview thumbnail, heavily documented in the UI to manage user expectations.Memory Management ProtocolsBatch processing capabilities support up to 20 concurrent files. This introduces significant risk regarding browser memory saturation. To prevent system crashes, the service explicitly revokes URL.createObjectURL() references immediately after the image blob is painted to the canvas, actively invoking garbage collection by nullifying image object references within the Promise.all resolution array.AI Background Removal Engine (backgroundRemovalService.ts)The AI background removal utility operates at the frontier of client-side capability. Media and Document ForensicsFor JPEG imagery, the application utilizes the piexifjs library. The service reads the binary array, isolating the ExifIFD and GPSIFD directories to map geolocation data, camera models, and timestamps into the human-readable <MetadataTable> component. The cleaning routine executes piexif.remove(jpegData), which safely truncates the metadata sectors while preserving the baseline image binary, avoiding the quality loss associated with re-encoding the image.For PDF documents, the pdf-lib module handles the deserialization of the internal node tree. PDFs house metadata in two primary locations: the internal Document Information Dictionary (containing the Author, Creator, and Producer fields) and the embedded Extensible Metadata Platform (XMP) XML stream. The cleaning mechanism resets the Information Dictionary entries to null, generates a blank, standardized XMP metadata stream to override the original, and re-saves the document. Similarly, DOCX metadata is purged by parsing the ZIP structure via JSZip and truncating the docProps/core.xml and docProps/app.xml files.AI Text Watermark and Stylistic Footprint ScrubberLarge Language Models occasionally inject invisible digital watermarks or adhere to highly specific stylistic footprints. Academic institutions and AI detection software scan for these hidden identifiers or rely on linguistic frequency distributions.The text scrubbing utility targets these anomalies on two fronts:Invisible Character Purge: Using precise Regular Expressions, the service parses pasted text and aggressively strips zero-width spaces, word joiners, and non-printable control characters that frequently reside in the Unicode ranges U+0000-U+001F, U+007F-U+009F, and specifically U+200B to U+200D. The algorithm guarantees that invisible delimiters cannot bypass the output stream.Stylistic Footprint Analysis: The tool leverages an internal dictionary map to flag "Tier 3 phrases"—multi-word boilerplate constructs such as "It is important to note," "In conclusion," or "As an AI language model". It provides a visual interface highlighting overly polished, uniform sentence structures, advising the user to inject human entropy through varied vocabulary and asymmetric sentence lengths.A persistent, high-contrast UI disclaimer is mandated above the result panel, explicitly stating: "This tool removes common metadata fields for privacy. It does NOT guarantee removal of all AI watermarks, cryptographic fingerprints, or steganographic identifiers embedded in pixel data or model weights."Cryptographic Password GeneratorThe password generator eschews external libraries, operating entirely on the client-side via the window.crypto.getRandomValues() API to generate cryptographically secure pseudo-random number arrays (CSPRNG). Standard functions like Math.random() are strictly prohibited due to mathematical predictability.The generator avoids arbitrary "strength" labels (e.g., "Weak," "Strong"), relying instead on raw mathematical entropy calculation. The entropy formula implemented within the component is defined as:$$E = L \times \log_2(R)$$Where $E$ represents the total entropy bits, $L$ is the length of the requested password string, and $R$ represents the total size of the active character pool (e.g., 26 lowercase + 26 uppercase + 10 digits + 32 symbols = 94). The <StrengthMeter> component visually maps this integer; an entropy threshold of $E \ge 80$ bits triggers the highest secure visual state.The application generates passwords in real-time, computing a new string instantly upon any state mutation—such as sliding the length constraint (8–128 characters) or toggling the symbol parameters. The tool includes a pronounceable mode algorithm that strictly alternates consonants and vowels to create memorable, albeit lower-entropy, strings. The history of the last 10 generated passwords is held exclusively in volatile React session state and is purposefully never persisted to localStorage, actively evaporating upon tab closure.Data-Driven Utilities: Currency and UnitsCurrency Exchange Engine (currencyRatesService.ts)The Currency Converter integrates with the Open Exchange Rates (OXR) API free tier. It relies on a strictly typed, bidirectional graph housed in /config/units.config.ts. Every unit (e.g., Meters, Kilograms, Fahrenheit) is assigned to a specific category and possesses definitive toBase(value) and fromBase(value) closure functions.This architecture guarantees mathematical precision. For example, temperature conversions do not rely on standard multiplicative constants but utilize specific linear equations:$$T_{\text{Celsius}} = (T_{\text{Fahrenheit}} - 32) \times \frac{5}{9}$$By centralizing the mathematical graph, extending the converter requires solely appending a new object definition to the configuration file, demanding zero modifications within the UI components. The tool features instantaneous bidirectional conversion and allows users to pin favorite unit pairs, which are serialized to localStorage.Percentage and Daily CalculatorsThe suite of daily calculators (Percentage Change, Discount, Tip, Margin/Markup) prioritizes frictionless interaction.
