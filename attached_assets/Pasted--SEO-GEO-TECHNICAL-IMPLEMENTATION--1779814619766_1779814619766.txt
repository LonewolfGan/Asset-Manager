───────────────────────────────────────────────
URL STRUCTURE
───────────────────────────────────────────────

Pattern: /{locale}/{verb}-{from}-to-{to}
Examples:
  /en/convert-pdf-to-docx
  /fr/convertir-pdf-en-docx        ← FR slugs use French verbs
  /en/compress-pdf
  /fr/compresser-pdf
  /en/remove-image-background
  /fr/supprimer-fond-image

Rules:
  - All lowercase, hyphens only (no underscores, no camelCase)
  - FR locale uses FR slugs, not EN slugs with /fr/ prefix
  - No trailing slash
  - Locale prefix always present (/en/, /fr/)
  - Root / redirects to /{detected-locale}/ (Accept-Language header, fallback /en/)
  - All redirect rules defined in next.config.js

/en/search?q= route:
  Simple client-side filter over tools.config.ts data
  Renders matching tool cards. No server-side search needed.
  Page exports generateMetadata() with noindex: true (avoid thin-content penalty)

HREFLANG & LOCALE ROUTING

Build a slugMap in tools.config.ts:

In next.config.js, i18n block:
  defaultLocale: "en"
  locales: ["en", "fr"]
  localeDetection: true

───────────────────────────────────────────────
ON-PAGE SEO — CONTENT RULES
───────────────────────────────────────────────

Every tool page <main> must contain, in order:

1. <h1> — Tool name only. No tagline. Exact match to primary keyword.
   Example: "PDF to DOCX Converter" / "Convertisseur PDF en DOCX"

2. <p class="tool-description"> — One sentence. Primary keyword used naturally.
   Benefit-first. Under 25 words.
   Example: "Convert PDF files to editable Word documents instantly,
   entirely in your browser — no uploads, no account required."

3. Tool interface (the actual functional area)

4. <section aria-label="How it works"> — 3 short steps, plain text.
   This content feeds the HowTo schema and targets "how to" featured snippets.
   DO NOT use a component with animations or icons — pure text + numbered list.

5. <AdSlot />

6. <section aria-label="About this tool"> — 150–200 word explanatory paragraph.
   Must contain:
   - Primary keyword in first sentence
   - Secondary keyword variant in second paragraph
   - Factual statements about the format/conversion (no fluff)
   - One mention of "free", "no signup", "browser-based" naturally
   This targets informational queries and provides crawlable text depth.
   In FR locale: full translation, not auto-translate garbage.

7. <AdSlot />

8. <FAQSection> — 5–7 questions. Rules:
   - Questions must match real search queries (use "how to", "can I", "is it safe")
   - Answers: 40–80 words each, plain text, no markdown inside
   - Last question always: "Is [Tool Name] free?" → Answer: Yes, always free, etc.
   - FR: full translation, not placeholders

Text density rule: minimum 300 words of crawlable text per tool page
(excluding UI labels, buttons, and nav). This is enforced by the
"How it works" + "About" + FAQ sections.

Internal linking:
  - Each tool page links to 2–3 related tools contextually in the "About" section
  - Example: PDF to DOCX page links to PDF Compressor and DOCX to PDF
  - Link text: the target tool's primary keyword, not "click here"
  - Implement via tools.config.ts: each tool has a relatedTools: string[] field

───────────────────────────────────────────────
PERFORMANCE — CORE WEB VITALS (direct ranking factor)
───────────────────────────────────────────────

LCP target: < 1.5s. FID/INP target: < 100ms. CLS target: < 0.05.

Font loading:
  Google Fonts via <link rel="preconnect"> + display=swap.
  Subset to latin + latin-ext only.
  In _document or layout: preload the woff2 of the primary weight.

Images:
  All static assets via next/image with explicit width/height (prevents CLS).
  OG images: static, pre-generated at build time (not dynamic routes).
  No layout shift from ad slots: AdSlot containers have fixed min-height
    (horizontal: min-height 90px, square: min-height 250px) even when empty.
    This is critical — ad slots without reserved space cause CLS failures.

WASM / heavy libs:
  @imgly/background-removal, pdfjs-dist, heic2any:
    → next/dynamic({ ssr: false, loading: () => <SkeletonLoader /> })
    → loaded only on the page that needs them
    → never in layout.tsx or _app

Script loading:
  No third-party scripts in <head> except Google Fonts preconnect.
  Ad scripts (future): load with next/script strategy="lazyOnload"
  No render-blocking resources.

HTTP headers (next.config.js headers()):
  Cache-Control: public, max-age=31536000, immutable → /_next/static/*
  Cache-Control: public, max-age=3600, stale-while-revalidate=86400 → /sitemap.xml
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: camera=(), microphone=(), geolocation=()

GEO — INTERNATIONAL SIGNALS
───────────────────────────────────────────────

The site targets global English + French-speaking markets.
French markets: France, Belgium, Switzerland, Canada (QC), Maghreb, West Africa.

Locale detection (middleware.ts):
  Read Accept-Language header.
  If fr or fr-* → redirect to /fr/{slug-fr}
  Default → /en/{slug-en}
  User can override via nav switcher → store in cookie "NEXT_LOCALE",
  cookie takes precedence over header on subsequent visits.

FR content rules:
  ALL user-facing strings must be real French — not machine-translated English.
  Tone: neutral, professional, direct (not "vous" overly formal, not "tu" informal
  — use "vous" for instructions, implied subject where possible).
  FR FAQ questions must reflect actual FR search phrasing, not translated EN queries.
  Example EN: "How do I convert PDF to Word?" 
  Correct FR:  "Comment convertir un PDF en Word ?"
  Wrong FR:    "Comment puis-je convertir PDF à Word ?" ← literal mistranslation

hreflang validation:
  After implementation, output a manifest of all hreflang pairs
  in /public/hreflang-manifest.json for QA purposes.
  Format: [{ "en": "/en/convert-pdf-to-docx", "fr": "/fr/convertir-pdf-en-docx" }]

───────────────────────────────────────────────
AI SEARCH ENGINES & GEO (GENERATIVE ENGINE OPTIMIZATION)
───────────────────────────────────────────────

Targets: Google AI Overviews (SGE), Perplexity, ChatGPT Search, Claude, Bing Copilot.

These engines extract answers from crawlable text. The content rules above
(HowTo schema, FAQPage schema, "About" section, robots.txt allowing AI crawlers)
already handle technical signals. Additional rules:

Answer-first writing: Every FAQ answer and "About" paragraph must open
with a direct, complete answer. No preamble.
  Wrong: "That's a great question. When it comes to PDF conversion..."
  Right: "PDF to DOCX conversion preserves text and basic formatting.
          Tables and images may require manual adjustment after conversion."

Factual density: Include concrete facts in About sections.
  Examples: file size limits, supported color depths, format specs, compatibility notes.
  AI engines prefer citing factual, specific content over vague marketing copy.

Named entity clarity: Always refer to tools by their full name on first mention
  per page: "EverydayTools Hub PDF to DOCX Converter" — this helps AI engines
  associate the answer with the specific tool/site.

No orphan pages: every tool must be linked from the homepage and from
  at least one other tool page (via relatedTools). AI crawlers follow links;
  unlinked pages get low crawl priority.

Freshness signal: Add a <time datetime="{ISO date}"> element to each tool page
  displaying "Last verified: {Month Year}" in the About section.
  Update this date in tools.config.ts at each deployment via new Date() at build time.
  This signals content currency to both Google and AI crawlers.
